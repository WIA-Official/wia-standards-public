# WIA-CODE-001 — 軌道アンカー2Dコード

**[English](README.md) · [日本語](README.ja.md) · [简体中文](README.zh-CN.md) · [繁體中文](README.zh-TW.md)**

> オープンで、パースペクティブ（見る角度）に強く、高容量な2次元機械可読コード——QRの代替として、
> AIカメラ／ARグラスの時代に向けて設計されており、**オフライン**利用が最も重要となる場面、
> すなわちインターネットのない子ども向けの本や、悪条件下でも読み取れる災害救援情報のために作られている。
>
> ステータス：**動作するリファレンス・プロトタイプ**（実機スマートフォンでの位置特定を確認済み）。
> これは今なお発展中の仕様書＋リファレンス実装であり、まだ凍結された標準ではない。

弘益人間 — *あまねく人類を利する。* アプリのインストールもネットワークも不要で誰もが読めるコードは、
すべての人のための選択である。

## なぜ新たな2Dコードが必要なのか

QRが主流であるのは、性能によってではなく普及率によるものだ。QRは白黒のみで規格化されており
（ISO/IEC 18004）、その正方形のファインダーパターンは直線走査によって読み取られるため、
パースペクティブの傾き、動き、低照度の下で性能が劣化する——これはまさにARグラス、動くカメラ、
現場・災害利用の条件そのものである。WIA-CODEは直線ではなく**円と中心点**によって読み取りを行い、
これによって3つの構造的な利点が得られる：回転不変性、単一のブルズアイからのクローズドフォームな
パースペクティブ復元、そして積分的（ノイズ平均化）検出である。

## それは何か

- **軌道アンカー位置特定（Orbit anchor localization）** — 中央の同心円状「ブルズアイ」（コア）＋
  四隅の「サテライト」（回転方向を示す「北極星」役のドーナツ形1個を含む）＋フォーマット情報を
  担う軌道リングから成る。Fast Radial Symmetry Transformによって検出され、サブピクセル精度の
  ホモグラフィへと精緻化される。急な視野角でサテライトが圧縮された場合でも、コア単体から
  **円錐束（conic-pencil）によるパースペクティブ復元**が行われる。
- **データ層** — ペイロード → フレーム（ヘッダー＋CRC16）→ リード・ソロモン誤り訂正 →
  データセル、という構成。外部エンジンを使わないスタンドアロンのリード・ソロモン／CRCコーデック
  （`rs.js`）を備える。
- **マルチレベルセル — 仕様上は定義されているが、使用してはならない。** 各データセルは1、2、
  または3ビット（2／4／8階調）を担い得る。**使用可能なのは `bpc:1`（白黒）のみである。**
  グレースケールモードはカメラでは原理的にデコードできない——階調判別の誤り下限（約14.7%）が
  ECC予算（約6.7%）を超えるため、コードは正しく捕捉された上で**decodeだけが永久に失敗する**。
  準拠エンコーダは `bpc:1` で出力しなければならない。wiacode.com のAPI／MCP／CLIは
  そもそも `bpc` をパラメータとして公開しておらず、1 に固定され呼び出し側からは変更できない。

## 測定結果（再現可能——`examples/benchmark.js` を実行のこと）

以下のWIA側の数値は、このフォルダ内のリファレンスコードによって生成されたものである。**QR側は
このキットだけでは再現できない**——QRエンコーダーを同梱していないため、`examples/benchmark.js` は
WIA単独で測定し、実行時にその旨を表示する。QRとの直接比較は `BENCHMARK.md` にあり、自分で再実行
するにはQRエンコーダーとQRデコーダーが別途必要である（本測定ではjsQRを用い、ZBarで相互検証した）。

**1ビットの列を使うこと。** 2／3ビットの列は仕様を記述する目的でのみ掲載している。これらは
**カメラでデコードできず**（上記参照）、印刷物や画面表示のコードに用いてはならない。
1コードあたりの正味ペイロードバイト数（各段階のデフォルトECC）：

| グリッド | 1ビット（ECC 25%） | 2ビット・頑健重視（ECC 50%） | 2ビット・最大容量（ECC 35%） | 3ビット（ECC 50%） |
|---|---|---|---|---|
| S（3728セル） | 344 | 458（×1.3） | 598（×1.7） | 690 |
| M（8848セル） | 824 | 1099 | 1432（×1.7） | 1646 |
| L（16016セル） | 1492 | 1994（×1.3） | 2590（×1.7） | 2994 |

QRはISO/IEC 18004によって1ビット（白黒）に固定されており、これに追随することはできない。

**QRとの頑健性比較**（同一ペイロード、同一の物理サイズ約440px、同一の劣化条件。QRはjsQRで、
WIAはリファレンスエンジンでデコード——詳細は`BENCHMARK.md`を参照）。総合デコード成功率
（劣化なしの条件を除く）：**QR 75%・WIA-1bit 95%**。（2ビットの行は意図的に省いている——
カメラでデコードできない以上、その頑健性の数値は使える指標ではない。）

- **WIAはパースペクティブで完勝** — ヨー角0〜50°まで全てデコード可能。QRは40°を超えると
  失敗する。これはARグラスや斜めに構えて使う場面に該当する。
- **WIAはノイズにも強い**（σ 30〜60ではQRが失敗する領域）——低照度・災害現場の条件である。
- **1ビットでの容量**：正方形のフットプリント（同一の設置面積）では、誤り訂正を揃えた条件（双方25%）でWIAはQRの
  **1.80倍**を格納する。QRが充填できない輪郭形状では最大**12.06倍**に達する（`BENCHMARK.md`
  セクションA-2を参照）。
- 正直な弱点：**同一の物理サイズ**では、WIAは**ブラー**と**極端な低解像度**で劣る。同一の物理サイズでは
  WIAのモジュールが**2倍小さい**（同じ面積にデータモジュールが約4.9倍）ためであり、その面積を
  ペイロードに充てているからである。これは形式の欠陥ではなく容量の
  選択にすぎない——**同一のデータ密度**（双方約350B）で比較すると、QRが1pxのブラーで失敗する
  のに対しWIAは3pxまで耐える。実測限界はQRが1モジュールあたり1.44px、WIAが1.68px——QRが
  最も得意とする軸でも差は17%にとどまる。

### カラー（色相）レイヤー——加算的な容量拡張、輝度はそのまま保持

> **カメラで読み取るコードには使用してはならない。** 色相レイヤーは `bpc≥2` を前提とするが、
> それはカメラでデコードできない（上記参照）。`bpc:1` では色相を載せられるセルが**構造上ゼロ**
> になる（`eligibleFromLuma` が空集合を返す）ため、準拠コードにこのレイヤーを適用すること自体が
> できない。ここに記載しているのは形式を説明するため、および将来のファイル間（非カメラ）経路の
> 可能性のためであり、製品版ジェネレーターでは公開していない。

グレースケールのペイロードの上に、独立した第2のペイロードが**色**に乗る。その仕組み（YCbCr）：
ドットの輝度Yがグレースケールの階調と一致するため、`toGray`は全く同じ輝度シンボルを復元する
——**グレースケールでのスキャン、白黒印刷、色覚異常の閲覧者であっても、ベースのペイロードは
一切失われない。** 色相はクロマ（色差）成分に*追加の*ビットを担う。デフォルトは**青黄
（Cb）軸上のK=2**——JPEGおよび印刷に対して最も頑健で、かつ色覚異常に完全に対応している。
測定結果（`examples/test-color.js`）：

| モード | S | M | L | 2ビット輝度比 |
|---|---|---|---|---|
| 2輝度（色相なし） | 458 | 1099 | 1994 | 1.00× |
| 2輝度＋1色相 | 567 | 1369 | 2488 | **×1.25** |
| 2輝度＋2色相 | 683 | 1644 | 2988 | ×1.50 |
| **3輝度＋2色相** | 1029 | 2459 | **4474** | **×2.25** |

- 通常のスキャン解像度において（ブラーを含めても）**JPEG 4:2:0のクロマサブサンプリングに耐える**
  ことを測定済み（M／Lグリッド）——これはあらゆるカラーコードにとって最大の脅威である。
- **正直な限界**：色相はピクセル数を必要とする——近距離／スクリーンショット／M〜Lグリッド向けの
  機能であり、遠距離・低解像度では真っ先に劣化する。失敗した場合でも、グレースケールのベース層は
  完全にデコード可能である（グレースフル・デグラデーション）。2つの色相プレーンはそれぞれ独立して
  誤り訂正される（RS 50%）。

## 使い方

```bash
# Node — data round-trip (encode → render → degrade → detect → decode)
node examples/test-codec.js         # 1-bit
node examples/test-multilevel.js    # 2/3-bit grayscale capacity
node examples/benchmark.js --md     # regenerate BENCHMARK.md

# Browser — install-free camera scanner (open over HTTPS, grant camera)
#   examples/scan.html + examples/wiascan-core.js  (self-contained, no CDN)
```

スキャナーエンジンが公開しているもの：
`WiaScan.detectAuto(imageData)` → `{ ok, text, hue, bitsPerCell, grid, shape, cellPx, corners, residPx, … }`
（スケール・グリッド・**形状**・階調・色検出を自動判定）、`WiaScan.generate(opts)`
（ペイロード → コードPNG）、および`WiaScan.renderTestCode(...)`。ブラウザ用の**ジェネレーター**
（`examples/generate.html`）と**スキャナー**（`examples/scan.html`）が同梱されている。

## 形状とコンテンツ——QRには構造的に不可能なこと

- **形状**：`square`（正方形）・**`round`（円形）**・**`heart`（ハート形）**（任意のシルエットが
  データマスクとなり、検出は放射状に行われるため形状に依存しない——QRの正方形ファインダーの
  せいで、QRを円形にすることは構造的に不可能である）。スキャナーは形状を自動検出する。円形は
  等しいバウンディングボックスにおいて正方形に比べ容量が約24〜28%減少するが、円形の物体
  （チップ、キャップ、バッジなど、正方形コードでは円に内接させなければならない対象）では
  むしろ有利になる。
- **コンテンツの種類／「コンフィグ・トゥ・コード」**：テキスト、URL、そして構造化された
  **SSH／API／MCPブートストラップ**ペイロード（コンパクトなJSON）——サーバー／API／エージェント
  設定一式をオフラインで1つのコードに収めて運ぶ。これはWIAのマシン・トゥ・マシン領域への
  足がかりであり、AIエージェント、ロボティクス、エアギャップ環境でのプロビジョニングのための、
  高容量・オフライン・無線サイレント・パースペクティブに強いマークである。
- **動画への埋め込み**：検出がパースペクティブ・回転・動きに対してQRよりはるかに寛容であるため、
  アニメーション／3D動画に合成されたWIAコードは実用上読み取り可能である——極端な複合的な動きの
  下ではすべてのフレームがデコードできるわけではないが、ライブスキャナーは1フレームさえ良好で
  あればよく、WIAはQRよりはるかに多くのそうしたフレームを捉える（動きに対する頑健性を
  最大化するには1ビットを使用のこと）。

## リファレンス実装（`reference/`）

純粋なJavaScriptで書かれており、Nodeとブラウザの両方で動作し、外部依存はない。

| ファイル | 役割 |
|---|---|
| `geometry.js` | 軌道ジオメトリ仕様＋レンダラー＋データセルのレイアウト |
| `frst.js` | Fast Radial Symmetry検出器＋サブピクセル／重心の精緻化 |
| `conic.js` | 同心円の円錐束（conic-pencil）によるパースペクティブ復元 |
| `locate.js` | アンカー位置特定 → モジュール→画像ホモグラフィ（`locateRobust`） |
| `codec.js` | データ層：フレーム＋RS＋マルチレベルセル＋較正済み分類 |
| `rs.js` | スタンドアロンのリード・ソロモン（GF256）＋CRC-16＋ブロックプラン（外部エンジン不要） |
| `degrade.js` | 計装済みの劣化処理（ベンチマーク／テストでのみ使用） |
| `jsQR.js` | サードパーティ製QRデコーダー、正面比較ベンチマークでのみ使用 |

## 先行技術とIPに関する正直な注記

同心円による機械可読コードには数十年にわたる先行技術が存在する（MaxiCode 1992、ShotCode、
TopCode、および学術的な円形フィデューシャルマーカー類）。同心リングコードに関する主要な特許
（US 7,621,459）は2025年に失効し、現在はパブリックドメインである。WIA-CODEが新規性を主張する
のは**あくまで**その具体的な軌道アンカー検出手法（FRST位置特定＋円錐束パースペクティブ復元＋
アンカー較正済みマルチレベルサンプリング）に限られ、「円で構成されたコード」そのものに
新規性を主張するものではない。本プロジェクトは特許出願なしのオープンソースとして公開されており、
商業的な主張を行う前には正式なフリーダム・トゥ・オペレーツ調査を実施することが推奨される。

## ロードマップ

- マルチレベルにおけるパースペクティブ頑健性の向上（矯正後のフレーム内でセルをサンプリングする）。
- グレースケールで分離可能なベース層の上に追加ビットを担う、オプションのカラー（色相）レイヤー。
- より多くのプラットフォーム向けのリファレンスデコーダー（WebAssembly、ネイティブ）、および
  候補となるマーカータイプとしてのKhronos OpenXRマーカートラッキング拡張への働きかけ。
