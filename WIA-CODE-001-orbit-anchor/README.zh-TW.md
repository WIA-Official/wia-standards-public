## 為何需要另一種二維碼？

QR 之所以普及，靠的是既有的市占率，而非效能表現。它在標準（ISO/IEC 18004）中被規定為僅限黑白，
其方形定位圖案是以直線掃描方式讀取，在透視傾斜、移動與低光源環境下判讀能力會下降——而這些正是
眼鏡裝置、移動中的攝影機，以及野外／災難現場使用時的典型條件。WIA-CODE 改以**圓形與圓心**而非
直線進行判讀，因而獲得三項結構性優勢：旋轉不變性、可由單一靶心以封閉解形式求得透視復原，以及
積分式（雜訊平均化）偵測。

## 這是什麼

- **軌道錨點定位**——由中央同心圓*靶心*（core）+ 四個角落*衛星點*（satellites，其中一個為甜甜圈形的
  「北極星」，用於指示旋轉方向）+ 一圈格式軌道環組成。以 Fast Radial Symmetry Transform 偵測，
  並精修至次像素等級的 homography；當衛星點因視角過於傾斜而遭壓縮時，僅憑核心即可透過**圓錐曲線束
  透視復原**求解。
- **資料層**——payload → frame（header+CRC16）→ Reed–Solomon 錯誤更正 → data cells。一套獨立的
  Reed–Solomon/CRC 編解碼器（`rs.js`）——不依賴外部引擎。
- **多階資料格——規格中有定義，但請勿使用。** 每個資料格可承載 1、2 或 3 位元（2/4/8 種灰階
  等級）。**唯一可用的是 `bpc:1`（黑白）。** 灰階模式在原理上無法以相機解碼：灰階判別的錯誤
  下限（約 14.7%）超出錯誤更正預算（約 6.7%），因此條碼可以正常鎖定，但**解碼會永遠失敗**。
  符合規格的編碼器必須以 `bpc:1` 輸出；wiacode.com 的 API／MCP／CLI
  根本不將 `bpc` 開放為參數——它被硬編碼為 1，呼叫方無法覆寫。

## 實測結果（可重現——執行 `examples/benchmark.js`）

下列 WIA 側的數字皆由本資料夾中的參考程式碼實際產生。**QR 側無法僅憑本套件重現**——其中並未附帶 QR
編碼器，因此 `examples/benchmark.js` 僅測量 WIA，並會在執行時說明這一點。與 QR 的正面對比見
`BENCHMARK.md`；若要自行重現，需另備 QR 編碼器與 QR 解碼器（本次測量使用 jsQR，並以 ZBar 交叉驗證）。

**請使用 1-bit 那一欄。** 2/3-bit 各欄僅用於說明規格本身；它們**無法以相機解碼**（見上文），
不得用於印刷或螢幕顯示的條碼。每個條碼的淨酬載位元組數（各層級採用預設 ECC）：

| 網格 | 1-bit (25% ECC) | 2-bit 穩健型 (50% ECC) | 2-bit 最大容量型 (35% ECC) | 3-bit (50% ECC) |
|---|---|---|---|---|
| S (3728 格) | 344 | 458 (×1.3) | 598 (×1.7) | 690 |
| M (8848 格) | 824 | 1099 | 1432 (×1.7) | 1646 |
| L (16016 格) | 1492 | 1994 (×1.3) | 2590 (×1.7) | 2994 |

QR 被 ISO/IEC 18004 標準凍結在 1 位元（黑白），無法跟進。

**與 QR 的穩健性比較**（相同酬載、相同實體尺寸約 440px、相同的劣化處理；QR 以 jsQR 解碼，WIA 以
參考引擎解碼——詳見 `BENCHMARK.md`）。整體解碼成功率（不含無劣化情境）：**QR 75%・WIA-1bit
95%**。（此處刻意省略 2-bit 一列——既然無法以相機解碼，其穩健性數值便不是可用的指標。）

- **WIA 在透視變形上完全勝出**——偏航角 0–50° 皆可解碼；QR 在超過 40° 後即失敗。這正是 AR 眼鏡／
  傾斜手持使用的情境。
- **WIA 在雜訊方面勝出**（在 QR 失敗的 σ 30–60 範圍內）——這正是低光源／災難現場的情境。
- **1-bit 下的容量**：在相同佔用面積的方形版面上，於錯誤更正對齊的條件下（雙方皆 25%），WIA 的
  容量是 QR 的 **1.80 倍**；在 QR 無法填滿的異形輪廓中最高可達 **12.06 倍**（詳見 `BENCHMARK.md`
  第 A-2 節）。
- 誠實列出弱項：在**相同實體尺寸**下，WIA 在**模糊**與**極端低解析度**上落後於 QR。原因是在相同實體尺寸下
  我們的模組**小一半**（同樣面積中資料模組約為 4.9 倍），我們把這部分面積用於負載。這是容量取捨，而非格式缺陷——在**相同資料密度**
  （雙方約 350 B）下比較，QR 在 1px 模糊即失敗，WIA 則可承受 3px。實測極限為：QR 可解碼至每模組
  1.44px，WIA 為 1.68px——即使在 QR 最擅長的面向上，差距也僅有 17%。

### 色彩（色相）層——附加容量，亮度維持不變

> **請勿用於相機掃描的條碼。** 色相層需要 `bpc≥2`，而後者無法以相機解碼（見上文）。在 `bpc:1`
> 下，可承載色相的資料格在**結構上為零**（`eligibleFromLuma` 回傳空集合），因此根本無法將此層
> 套用於符合規格的條碼。此處記載僅用於說明格式，以及為將來可能的檔案對檔案（非相機）通道保留；
> 正式版產生器並未提供此功能。

第二組獨立的酬載，會疊加在灰階酬載之上，以**色彩**方式承載。其中的訣竅在於（YCbCr）：圓點的亮度 Y
等於灰階等級，因此 `toGray` 能還原出完全相同的亮度符碼——**無論是灰階掃描、黑白列印，或是色盲
使用者，都不會遺失任何基礎酬載。** 色相則在色度中承載*額外*的位元。預設為**在藍黃（Cb）軸上
K=2**——這是對 JPEG 與列印最穩健、且對色盲使用者完全安全的設定。實測數據（`examples/test-color.js`）：

| 模式 | S | M | L | 相較於 2-bit luma |
|---|---|---|---|---|
| 2-luma (no hue) | 458 | 1099 | 1994 | 1.00× |
| 2-luma + 1-hue | 567 | 1369 | 2488 | **×1.25** |
| 2-luma + 2-hue | 683 | 1644 | 2988 | ×1.50 |
| **3-luma + 2-hue** | 1029 | 2459 | **4474** | **×2.25** |

- **能撐過 JPEG 4:2:0 色度次取樣**（在一般掃描解析度下實測，含 M/L 網格，以及加上模糊的情況）
  ——這是任何彩色條碼最主要的風險來源。
- **誠實的界線**：色相需要足夠的像素——這是一項適用於近距離／螢幕截圖／M–L 網格的功能，在遠
  距離／低解析度時會最先劣化。當色相失效時，灰階基礎層仍可完整解碼（優雅劣化）。兩個色相平面
  各自獨立進行錯誤更正（RS 50%）。

## 使用方式

```bash
# Node — data round-trip (encode → render → degrade → detect → decode)
node examples/test-codec.js         # 1-bit
node examples/test-multilevel.js    # 2/3-bit grayscale capacity
node examples/benchmark.js --md     # regenerate BENCHMARK.md

# Browser — install-free camera scanner (open over HTTPS, grant camera)
#   examples/scan.html + examples/wiascan-core.js  (self-contained, no CDN)
```

掃描引擎提供以下介面：
`WiaScan.detectAuto(imageData)` → `{ ok, text, hue, bitsPerCell, grid, shape, cellPx, corners, residPx, … }`
（自動判斷縮放比例、網格、**形狀**、階數與色彩偵測）、`WiaScan.generate(opts)`（酬載 → 產生條碼
PNG），以及 `WiaScan.renderTestCode(...)`。並提供瀏覽器版的**產生器**（`examples/generate.html`）與
**掃描器**（`examples/scan.html`）。

## 形狀與內容——QR 在結構上辦不到的事

- **形狀**：`square`（方形）・**`round`**（圓形）・**`heart`**（愛心形）（任何輪廓都可以作為資料
  遮罩；偵測是以徑向方式進行，因此與形狀無關——QR 的方形定位圖案讓 QR 不可能做成圓形）。掃描器會
  自動偵測形狀。在相同外接框大小下，圓形的容量比方形少約 24–28%，但在圓形物件（晶片、瓶蓋、徽章
  等）上反而*勝出*，因為方形圖案在這類場合必須內接於圓形之中。
- **內容類型／「config-to-code」**：文字、URL，以及結構化的 **SSH / API / MCP-bootstrap** 酬載
  （精簡 JSON 格式）——將完整的伺服器／API／代理設定，以離線方式收納在單一條碼中。這正是 WIA
  切入機器對機器場景的利器：一種高容量、離線、無 RF 訊號、抗透視變形的標記，適用於 AI 代理、
  機器人，以及實體隔離（air-gapped）環境的佈建作業。
- **可嵌入影片**：由於在透視變形、旋轉與運動下的偵測容忍度遠優於 QR，將 WIA 條碼合成進動畫／3D
  影片中，在實務上是可判讀的——並非每一格畫面在極端複合運動下都能解碼，但即時掃描器只需要一格
  判讀成功的畫面即可，而 WIA 能捕捉到的成功畫面遠多於 QR（若要最大化運動穩健性，可使用 1-bit）。

## 參考實作（`reference/`）

純 JavaScript 實作，可在 Node 與瀏覽器中執行，無外部相依套件。

| 檔案 | 用途 |
|---|---|
| `geometry.js` | 軌道幾何規格 + 渲染器 + 資料格版面配置 |
| `frst.js` | Fast Radial Symmetry 偵測器 + 次像素／質心精修 |
| `conic.js` | 同心圓圓錐曲線束透視復原 |
| `locate.js` | 錨點定位 → module→image homography (`locateRobust`) |
| `codec.js` | 資料層：訊框 + RS + 多階資料格 + 校準分類 |
| `rs.js` | 獨立的 Reed–Solomon (GF256) + CRC-16 + 區塊配置 (無外部引擎) |
| `degrade.js` | 帶量測工具的劣化模擬 (僅供基準測試／測試使用) |
| `jsQR.js` | 第三方 QR 解碼器，僅用於正面對比基準測試 |

## 誠實揭露：先前技術與智慧財產權說明

同心圓機器可讀碼已有數十年的先前技術（MaxiCode 1992、ShotCode、TopCode，以及學術界的圓形基準
標記）；一項關鍵的同心圓環條碼專利（US 7,621,459）已於 2025 年到期，現屬公共領域。WIA-CODE
**僅**在其特定的軌道錨點偵測方法（FRST 定位 + 圓錐曲線束透視復原 + 錨點校準的多階取樣）上主張
新穎性，而非主張「以圓形構成的條碼」本身具有新穎性。本專案以開放原始碼形式發布，未申請專利；
在提出任何商業主張之前，建議先進行正式的實施自由度（freedom-to-operate）審查。
